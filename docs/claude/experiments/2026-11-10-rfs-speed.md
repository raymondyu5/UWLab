## Changes
- Removed per-env GPU->CPU syncs: `RFSEvalCallback._on_step` (one stacked transfer), `RFSWrapper.step` episode logging and `any_reset` reuse, `EnvMetrics.get_metrics_tensors()`. Not separately measured; formatter/other overheads were already small, so expect only a minor gain.
- Opt-in bf16 autocast for CFM inference: `rfs.cfm_autocast: true` (or CLI `--cfm_autocast` on train.py / play_rfs_wrapper.py), `RFSWrapper(cfm_autocast=...)`.
  - RK2 57.5 -> 43.2 ms (-25%). Totals 151 -> 117 ms in that run, but physics also moved 89 -> 71 ms with no change, so only the RK2 delta is trustworthy.
  - Quality: cube eval, 320 episodes, same seed: fp32 0.703, bf16 0.716 (noise ~0.025). Only checked on cube; re-check per task before using for others.
- Tried CUDA-graph replay of the RK2 loop: output identical to eager, no speedup (55.7 vs 57.5 ms; 41.6 vs 43.2 with bf16). The UNet is already `torch.compile`d and compute-bound. Removed.

## Physics: where env.step time goes (scripts/profile/profile_env_step.py, 512 envs, sync-bracketed so absolute ms are inflated)
Per env.step (6 substeps): sim.step 23.7, scene.update 21.9 (7 contact sensors ~2.8 each), scene.write_data_to_sim 19.5 (robot 16, rigid objects ~0.2 each), obs 3.9, reward 3.0. So about two thirds of env.step was Python-side per-substep bookkeeping, not PhysX.

## fast_substeps (opt-in): `rfs.fast_substeps: true` or CLI `--fast_substeps`, `RFSWrapper(fast_substeps=...)`, module `grasp/mdp/fast_step.py`
- Contact sensors update only on the last substep (all grasp-task consumers read `sensor._data` after the substep loop; `history_length=3` buffers are unused). Note: setting `update_period=decimation*dt` instead is NOT equivalent, because `reset` marks sensors outdated and shifts the update phase to substep 1.
- Robot `write_data_to_sim` only on the first substep of each env.step (action constant, all actuators implicit; skipped if wrenches active or any non-implicit actuator).
- Result: env.step 74 -> 44 ms (-40%); scene.update 21.9 -> 7.1, write_data_to_sim 19.5 -> 5.5, sim.step unchanged (~23).
- Equivalence: deterministic rollout checksum identical (reward_sum -67.834846, joint_pos_sum 1394.343239; contact forces were 0 in that rollout so it is weak for contacts). Cube RFS eval, 320 episodes: baseline 225/320 and fast 225/320, success_ever 238 both, n_grasped 0.746875 both (jobs 43109905). Multi-task check below.
- Credit card (job 43110140, same 64 envs x random_5_trials): base 237/320 (0.741, success_ever 283), fast 229/320 (0.716, ever 278). An independent baseline run on 10-30 gave 235/320 (0.734), so baselines agree to ~2 episodes while fast is 6-8 lower; within sampling noise (SE ~8 episodes) but NOT the exact match seen on cube. **Unresolved**: needs repeated base/fast runs (more seeds/episodes) once klone is back. Until then `fast_substeps` stays opt-in (default off) and should not be assumed behavior-preserving on all tasks.
- Same-node A/B (job 43110105): physics_step_ms (4 env.step per PPO step) base 86.0 and 85.8 vs fast_substeps 60.2 (-30%). The CFM and total columns of that job are invalid (still in torch.compile warmup).
- A fast+bf16 training run (job 43110052, different node) showed 122 ms/PPO step (physics 67, CFM RK2 50) vs 151 in the first baseline profile; node variance is ~15%, so treat the real end-to-end gain as roughly 20-30%.
- Bug found by the eval run: module splits (eval_plots/cfm_loader) broke `play_rfs_wrapper.py` (imports eval_callback as a package); fixed with try-relative/bare imports.

- **fast_substeps equivalence settled.** Credit card, 64 envs x random_5_trials, seed-matched (job 43110158): seed1 base 244/320 = fast 244; seed2 236 = 236; seed3 232 = 232; success_ever and n_grasped also identical. Baseline rerun of seed 1 = 244 (deterministic). The earlier 237 vs 229 gap came from unmatched seeds, not from fast_substeps. Combined with the cube result (225 = 225) -> `fast_substeps` is now **default on** (`rfs.fast_substeps: false` disables). Skipobs seeds in that job did not complete (timeout), so `skip_intermediate_obs` stays opt-in/unvalidated.
- **End-to-end same-node A/B (job 43110105, 512 envs, ms per PPO step = 4 env steps)**: baseline 149-150 (physics 87-88, CFM RK2 57.6), fast+bf16 116-117 (physics 61-62, RK2 50.6), baseline rerun 149-150 again. **-22% per PPO step (1.28x)**. bf16 stays opt-in (changes numerics; validated on cube only); fast_substeps alone gives physics -30% (about -17% per PPO step).
- **Env scaling (job 43110159, fast+bf16)**: 512 envs 118 ms, 1024: 148 ms, 2048: 241 ms per PPO step -> 0.231, 0.145, 0.118 ms per env-step (1.96x throughput at 2048 vs 512; CFM scales linearly, physics sublinearly). 4096 timed out. Larger num_envs is the biggest remaining throughput lever if PPO batch size can change.

## 4096 envs and repeat baseline (jobs 43141492, 43136092)
- 4096 envs (fast_substeps+bf16, job 43141492, 25 min window): 433 ms per PPO step (physics 98, CFM RK2 318) = 0.106 ms per env-step, vs 0.118 at 2048 and 0.231 at 512. Throughput saturates above ~2048 envs (only +11% from 2048 to 4096) because CFM scales linearly and is 73% of the step at 4096; physics per PPO step only grows 61 -> 98 ms over 8x envs.
- Repeat baseline in the A/B job (4th window) landed at ~154.5 ms vs ~150.5 for the first baseline window (+2.6% drift), so the ~20% fast+bf16 gain is outside the run-to-run spread.
- Where the limit is now: at 512 envs per PPO step ~66 ms physics (PhysX ~23 ms x4 unchanged, ~40 ms Python bookkeeping now mostly removed) + ~48 ms CFM (bf16, torch.compile, compute-bound). Remaining levers all change behavior: fewer CFM integration steps / smaller UNet (policy change, needs quality sweep), PhysX dt/decimation/solver settings (dynamics change). Not pursued.

## Measured default-only speedup (job 43146618, ab_default; interleaved base / default / base / default, 512 envs)
Steady-window means, ms per PPO step: baseline (--no_fast_substeps) physics 68.3, CFM RK2 59.0, total 130.6; default (fast_substeps, fp32) physics 54.5, RK2 58.8, total 116.5. So the default alone is **-10.8% per PPO step (1.12x)**, physics -20%. This replaces the earlier derived "15-17%" figure, which was too high: that estimate mixed windows from a slower node (physics 88 ms baseline); this job ran on a faster node (physics 68 ms baseline) where fixed per-substep overhead is a smaller share. Gain from fast_substeps therefore varies by node (~11-17%); bf16 adds ~10 ms (RK2 -9.5 ms) on top. Both repeated baseline windows agreed (129.1 / 129.1 total), exit 124 = last window's timeout.
